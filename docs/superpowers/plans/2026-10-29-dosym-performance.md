# DosYm Performance Implementation Plan

> **Status (29 October 2026):** P0, P1 and P2 implemented locally. P3 first-screen work is implemented and measured; remaining P3 items are listed below. No deployment or push was performed.

**Goal:** Устранить задержки интерфейса и рывки аватара, сохранив координаты, правильную длительность жестов, языки, доступность и отзыв материалов.

**Architecture:** Сначала измерить production-сборку, затем убрать постоянную работу сцены в покое и блокирующую подготовку движения. Оптимизировать загрузку и запросы по результатам профиля. Сохранять исходный авторский инструмент и единственный поддерживаемый источник аватара; генерируемую папку `pwa/public/avatar/` вручную не менять.

**Tech Stack:** Existing Next.js/React, Three.js, FastAPI, SQLite/PostgreSQL, IndexedDB, Playwright. Новые библиотеки вводить только после измерения необходимости.

## 1. Что установлено при обследовании

Дата: 29 октября 2026 года. Это обследование исходников и короткие локальные замеры, не полный CPU/GPU-профиль пользовательского браузера.

| Наблюдение | Доказательство | Вывод |
|---|---|---|
| Локальный запуск использует `next dev` | `scripts/start-pwa.ps1` | Компиляция и инструменты разработки могут увеличивать задержки. Сначала сравнить с production, не приписывать им все лаги. |
| Сцена запускает непрерывный `requestAnimationFrame` с `renderer.render` | `web/avatar.html`, функция `draw` | Даже неподвижный аватар требует постоянных GPU-кадров. |
| PWA-адаптер подавляет render только при `document.hidden`, но оставляет RAF | `pwa/scripts/prepare-avatar.mjs` | Пауза и уход сцены за пределы видимой области не останавливают цикл. |
| Iframe создаётся сразу | `pwa/features/player.tsx` | На телефоне тяжёлая сцена загружается даже ниже первого экрана. |
| Подготовка всех кадров синхронна | `web/rig-motion.mjs:bakeRigMotion`, вызов из `web/avatar.html` | Кандидат на блокировки главного потока при первом запуске длинных клипов; измерить длительность. |
| DPR ограничен значением 2, antialias включён | `web/avatar.html` | На экранах высокой плотности объём GPU-работы возрастает; нужен измеренный режим качества. |
| Все основные экраны импортируются в один клиентский workspace, Supabase SDK импортирован статически | `pwa/features/workspace.tsx`, `pwa/lib/client.ts` | Потенциально лишний стартовый JS, включая экраны и провайдер, которые посетителю сейчас не нужны. |
| Все клиентские запросы и ответы API используют `no-store` | `pwa/lib/client.ts`, `backend/api.py` | Повторное получение одного публичного движения не использует HTTP-валидацию. Приватные ответы обязаны оставаться закрытыми. |
| На экранах материалов есть опросы каждые 4/6/8 секунд | `pwa/features/materials.tsx` | Скрытые вкладки продолжают опрашивать сервер; нужен адаптивный опрос. |

Размеры на диске, **не размеры реальной сетевой передачи**:

- GLB аватара: 2 900 276 байт; 7 312 треугольников, 3 примитива, 80 суставов.
- Публичная копия Three.js: 1 272 972 байта.
- Шрифт NotoSans TTF: 2 049 096 байт.

Короткий тест API: по пять последовательных GET с повторным использованием соединения.
Каталог: медиана 8,1 мс, максимум 106,1 мс, декодированное тело 255 байт.
Motion «сәлем»: медиана 51,5 мс, максимум 145,1 мс, декодированное тело 212 334 байта.
Это localhost, один клип, без сетевого ограничения. Эти данные не доказывают, что API никогда не тормозит, но не оправдывают начало с замены БД.

## 2. Порядок реализации

### P0 — воспроизводимые измерения и production-режим

**Файлы:** `scripts/start-pwa.ps1`, `scripts/stop-pwa.ps1`, `pwa/package.json`; новый сценарий измерения `pwa/scripts/profile-performance.mjs`; отчёты в игнорируемой папке данных.

- [ ] Зафиксировать устройство, браузер и режим. Выполнить одинаковые сценарии в используемом встроенном браузере и отдельно в Edge/Chrome, чтобы отличить особенности окружения от приложения.
- [x] Добавить явный выбор Development/Production в запуск. Для Production сначала сборка, затем `next start`; роли и режим хранения backend этим переключателем не менять.
- [x] Проверить локальный реестр процессов и останавливать только зарегистрированный DosYm frontend.
- [x] Снять лабораторный сценарий «Сәлем»: первый экран, загрузка и подготовка 56 кадров, пауза, простой и ресурсы браузера. Пользовательская база не изменялась.
- [ ] Снять также повторный/длинный клип, ввод 100 символов, смену языка/словарь, CPU/GPU, память, интервалы реального render и отдельно встроенный браузер/телефон. RAF не считать числом отрисованных кадров.

**Результат:** отчёт «до» и возможность воспроизвести лаг. Изменения последующих этапов сравниваются на том же устройстве и режиме.

### P1 — убрать непрерывный рендеринг в покое

**Файлы:** `web/avatar.html`, при необходимости небольшой чистый модуль политики рендера в `web/`; адаптер `pwa/scripts/prepare-avatar.mjs`, `pwa/features/player.tsx`.

- [x] Добавить проверку расписания кадров для покоя, скрытия и уничтожения сцены; проверить play/pause/resume и выход.
- [x] Перерисовывать сцену только по запросу или во время движения; в покое и на паузе останавливать RAF.
- [x] Останавливать цикл при скрытой вкладке или iframe вне экрана; при возвращении отправлять видимость отдельно и не возобновлять жест автоматически.
- [x] Объединить запросы отрисовки и цикл воспроизведения; сохранить исходный FPS.
- [x] Прогнать JS-кинематику и браузерные pause/resume сценарии; Python проверка motion API проходит.

**Результат:** неподвижная сцена не рисует непрерывно; play/resume начинают кадры без задержки. Это первый этап исправления самого GPU-потребления.

### P2 — подготовка движения без зависания интерфейса

**Файлы:** `web/rig-motion.mjs`, `web/avatar.html`, `pwa/features/player.tsx`.

- [x] Замерить подготовку клипа на 56 кадровых позициях; выделить её порции времени. В текущем профиле порции занимают примерно 0,5–5,2 мс.
- [x] Сохранить переиспользование готовой дорожки по версии координат/пайплайна, скелету и калибровке; проверки кэша и пользовательских правок проходят.
- [x] Разбить подготовку на порции по два кадра, уступать управление браузеру и отменять устаревший клип.
- [x] Worker не понадобился: в профиле нет длинных задач подготовки дорожки после разбиения.
- [x] Синхронная и асинхронная дорожки совпадают, исходные кадры, порядок и FPS сохраняются; добавлена проверка паузы во время подготовки.

**Результат:** интерфейс реагирует во время подготовки; повторное воспроизведение использует кэш. Worker — условный шаг по измерениям, не обязательная переделка всего 3D.

### P3 — быстрее первый экран и загрузка аватара

**Файлы:** `pwa/features/player.tsx`, `pwa/features/workspace.tsx`, `pwa/lib/client.ts`, `pwa/app/globals.css`, `pwa/scripts/prepare-avatar.mjs`, `pwa/public/sw.js`.

- [x] Загружать iframe/GLB только после выбора жеста; заранее показывать лёгкую заглушку, сохраняя размеры проигрывателя.
- [x] Разделить загрузку экранов видео-загрузки и материалов; Supabase SDK теперь импортируется только в режиме Supabase.
- [x] Переключить приложение и офлайн-экран на системный sans-serif. Шрифт Noto больше не запрашивается браузером; его исходный файл оставлен в проекте.
- [ ] Отдельно замерить сжатие production JavaScript аватара и его сетевой трафик через HTTPS.
- [ ] Если профиль показывает GPU-ограничение, ввести ограниченный DPR/частоту кадров для слабых устройств. Проверить читаемость пальцев. 7 312 треугольников сами по себе не основание начинать с упрощения модели.

**Результат:** текст и элементы управления доступны раньше тяжёлой сцены; качество жеста сохраняется. Оптимизация текстур/геометрии — только при подтверждённой необходимости.

### P4 — повторные запросы, сериализация и масштабирование словаря

**Файлы:** `pwa/lib/client.ts`, `pwa/features/workspace.tsx`, `pwa/lib/gesture-search.ts`, `backend/api.py`, `backend/store.py`, `pwa/features/offline.tsx`.

- [ ] Добавить повторное использование загруженных публичных клипов по `id + version` и объединение одновременно идущих одинаковых запросов.
- [ ] Ввести ETag/304 и сжатие публичных ответов с обязательной ревалидацией. При отзыве/смене версии инвалидировать сетевой и prepared-кэш. Не применять публичное кэширование к сессиям, личным материалам, видео и модерации.
- [ ] Для больших клипов измерить цену JSON → массивы → postMessage; при существенной цене спроектировать версионированный бинарный формат/TypedArray. Сначала сравнить со сжатым JSON.
- [ ] Увеличивать каталог в тесте до 1 000/10 000 меток. При необходимости построить поисковые ключи один раз при изменении каталога, вместо повторной нормализации всех меток; большие списки выводить порциями.
- [ ] Не читать полные body-pose метаданные ради тонкого списка каталога, если это станет заметно в профиле БД. До измерений миграция/замена БД не нужна.

**Результат:** повторный жест не скачивается и не подготавливается заново; латинский поиск остаётся отзывчивым на растущем каталоге; отзыв материала продолжает работать.

### P5 — фоновые опросы и финальная приёмка

**Файлы:** `pwa/features/materials.tsx`, при необходимости общий hook опроса; тесты PWA/аватара.

- [ ] Приостанавливать polling скрытой страницы и офлайна, применять задержку после ошибок, не запускать следующий запрос до завершения предыдущего.
- [ ] Опросивать чаще только переходные состояния обработки; после готовности/отказа снижать частоту и обновлять при возврате фокуса.
- [ ] Повторить базовые замеры в production и на телефоне. Сохранить сравнительный отчёт и скриншоты.
- [ ] Пройти языки, поиск, pause/resume, офлайн, Google-вход, роли, модерацию и отзыв на тестовом наборе. Пользовательские материалы не использовать как расходные тестовые данные.

## 3. Критерии приёмки

Это целевые бюджеты, а не уже достигнутые показатели. После P0 зафиксировать эталонные устройства и сетевые условия.

- В покое и на паузе — нет непрерывных вызовов render после завершения переходов.
- Во время набора текста/смены языка — нет зависаний из-за подготовки клипа; ориентир INP не хуже 200 мс.
- Во время движения — ориентир не ниже 50 FPS на эталонном ПК и 30 FPS на среднем телефоне, без изменения длительности исходного жеста. Измерять actual renders и пропуски кадров.
- Повторный запуск уже подготовленного жеста — ориентир до 300 мс от действия до начала движения; первый запуск измерять отдельно от загрузки модели.
- Ориентиры первого экрана на согласованной мобильной сети: LCP до 2,5 с, CLS до 0,1. Указать, где используются лабораторные данные, а где реальные пользовательские.
- Память/WebGL-контексты не растут без ограничения после 20 циклов открытия и закрытия проигрывателя.
- Координаты, порядок и длительность клипов, пальцы/кисти, языки, роли, отзыв и офлайн остаются корректными.

## 4. Что делать первым

Первый пакет: **P0 → P1 → измерение P2**. Затем по профилю P2/P3; сетевые и масштабные оптимизации P4/P5 — следующим пакетом. Публикация на Vercel сама по себе не устраняет клиентскую GPU-нагрузку.

Не начинать с переписывания на другой фреймворк, смены БД, удаления координат, ускорения жеста или массового сокращения костей/пальцев. Каждую оптимизацию вводить отдельным измеримым изменением с возможностью отката через Git.
